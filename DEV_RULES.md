# DEV_RULES.md

Документ описывает обязательные правила для разработки лендинга на Astro в этом пайплайне.

## 1. Архитектура
1. Строить лендинг на Astro-компонентах.
2. Выносить повторяющиеся блоки в `src/components/`.
3. Делать страницу модульной, читаемой и легко поддерживаемой.
4. Не объединять весь лендинг в один большой файл без необходимости.

## 2. Контент и структура
1. Собирать лендинг как набор отдельных секций: hero, benefits, cases, FAQ, CTA, footer.
2. Не смешивать контент и разметку без необходимости.
3. Если есть карточки, отзывы, FAQ или другой однотипный контент, хранить данные отдельно и рендерить их через массивы или объекты.
4. Если контента много и он однотипный, использовать Content Collections или аналогичную структуру данных.

## 3. Верстка
1. Делать упор на HTML и CSS.
2. Использовать семантическую структуру: `header`, `main`, `section`, `nav`, `footer`.
3. Соблюдать правильную иерархию заголовков.
4. Писать понятные, предсказуемые классы.
5. Делать верстку адаптивной по принципу mobile-first.
6. Проверять отсутствие горизонтального скролла и читаемую типографику на всех брейкпоинтах.

## 4. Стили
1. Использовать либо scoped styles внутри компонентов, либо единый глобальный CSS-подход.
2. Не смешивать хаотично разные подходы к стилям без причины.
3. Поддерживать единые design tokens, переменные и правила отступов/типографики.
4. Для site-wide стилей использовать отдельный глобальный файл, если это упрощает поддержку.

## 5. JavaScript
1. Подключать JavaScript только там, где он реально нужен.
2. Не создавать лишние client-side islands.
3. Не добавлять framework-specific hydration без явной необходимости.
4. Если нужен интерактив, использовать простой vanilla JS, который легко перенести в финальный HTML.

## 6. Доступность и качество
1. Поддерживать accessibility по умолчанию.
2. Добавлять `alt` к изображениям.
3. Следить за контрастом, фокус-стилями и клавиатурной навигацией.
4. Использовать `aria-` атрибуты только там, где они действительно нужны.
5. Проверять, что интерфейс остаётся понятным без визуальных эффектов и скриптов.

## 7. Static-first
1. Делать лендинг статически переносимым.
2. Не завязываться на Astro runtime, серверные роуты или backend-логику.
3. Держать проект таким, чтобы итог можно было собрать в чистый HTML без рефакторинга.
4. Не использовать Astro-фичи, которые сложно перенести в raw HTML, если они не нужны для финального результата.

## 8. WordPress compatibility
1. Проектировать структуру так, чтобы её можно было вставить в WordPress как HTML-блок или HTML on page.
2. Минимизировать сложную компонентную связность и скрытые зависимости.
3. Не рассчитывать на server-side поведение на стороне WordPress.
4. Держать CSS и JS в форме, которую можно легко перенести вместе с HTML.
5. Не использовать решения, которые ломаются при вставке в статический HTML-контейнер WordPress.

## 9. Ограничения
1. Не добавлять лишние библиотеки и зависимости без необходимости.
2. Не использовать сложные анимации и эффекты, если они не входят в задачу.
3. Не переусложнять архитектуру ради технической красоты.
4. Не дублировать один и тот же смысл в нескольких местах кода.

## 10. Итоговое правило
Если есть выбор между “умным” решением и простым решением, выбирать то, которое:
1. легче поддерживать,
2. легче экспортировать в HTML,
3. легче вставить в WordPress,
4. не ухудшает качество верстки и UX.
